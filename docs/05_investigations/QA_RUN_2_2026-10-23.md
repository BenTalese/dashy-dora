## 1. High

### QA2-01 — Stored XSS: an image data-URL's declared mimetype is served back verbatim
- **Status (2026-10-24): FIXED** — image routes serve through `infrastructure/data_url.py` (raster types only).
- **Evidence:** LIVE.
- **Repro:** as any member, `POST /api/recipes` with
  `{"name":"x","image":"data:text/html;base64,PHNjcmlwdD5hbGVydChkb2N1bWVudC5jb29raWUpPC9zY3JpcHQ+"}`
  → 201. Then `GET /api/recipes/<id>/image` → **200, `Content-Type: text/html`, body
  `<script>alert(document.cookie)</script>`**.
- **Why it's exploitable:** the page CSP is `script-src 'self' 'unsafe-inline' 'unsafe-eval'`, and the
  `dora_csrf` cookie is readable by script. A member who gets an admin to open that URL can run script
  on the app's origin and call admin APIs, e.g. `PATCH /api/users/<me> {"is_admin":true}`. (The
  escalation chain is STATIC; the HTML being served is LIVE.)
- **Where:** stored unchecked in `features/recipes/create_recipe.py:299`, `recipes/update_recipe.py:389`,
  `products/create_product.py:134`, `auth/update_me.py:230`, `stores/manage_stores.py:153/229`. Served
  with the stored mimetype in `products/get_product_image.py:53`, `recipes/get_recipes.py:1859/1892`,
  `users/get_user_image.py:61`, `stores/manage_stores.py:359`. Some paths check only for a `data:image/`
  prefix, which still lets `data:image/svg+xml` with an inline `<script>` through (STATIC).
- **Fix direction:** one shared validator. Allowlist `image/png|jpeg|webp|gif`, reject SVG, and
  re-encode or sniff the bytes. On serve, set the content type from the sniffed type, never the stored
  string, and add `Content-Disposition: inline` plus a sandbox CSP on image responses. Enforce it in
  one place, not per feature (R-001/R-003).

### QA2-02 — Anyone can self-register and immediately read and write all household data
- **Evidence:** LIVE.
- **Repro:** with no session, `POST /api/auth/register {"username":"qa2eve","password":"longpassword9"}`
  → 200, and the caller is logged in. `GET /api/stock-items` → 200 with the household's data.
- **Where:** `features/auth/register_user.py:242`. There is no "registration open" toggle, no invite,

### QA2-03 — Password-reset link poisoning via the `Origin` header (when `public_url` is unset)
- **Evidence:** LIVE.
- **Repro:** `POST /api/auth/forgot-password {"email":"sam@example.com"}` with header
  `Origin: https://evil.example` → 204. The dry-run email in the server log contains
  `https://evil.example/#/reset-password?token=yAT3T-…`.
- **Where:** `infrastructure/auth_helpers.py:263` (`public_base_url()` falls back to the request's
  `Origin`). Production startup validation does not require `public_url`.
- **Fix direction:** never build an emailed link from request headers. Require `public_url` for any
  email that carries a token (refuse to send, with an admin-visible error), or fall back to a
  configured value only.

### QA2-04 — Changing a password does not revoke other sessions
- **Evidence:** LIVE.
- **Repro:** log `sam` in on session A and on session B. From B, `POST /api/auth/me/password` → 204.
  Session A still gets **200 on `/api/stock-items` and 200 on `/api/auth/me`**.
- **Static extension:** the same gap applies after a password *reset*, a deactivation and a user
  delete. The middleware only checks that `user_id` is present in the session; the staleness check runs
  only in `get_me` and `require_admin`, and evidently doesn't fire on a change. The permanent session
  lasts 31 days.
- **Overlaps:** FU-654 (the hand-rolled session→User resolver) and FU-655 (deactivation only enforced in
  two places). This adds the password-change and password-reset cases, which FU-655 does not cover.
- **Fix direction:** resolve the user once in the global `before_app_request` (FU-654). Check the
  active flag, existence and a password-version stamp there. Bump the stamp on password change and on
  reset.

### QA2-05 — The "Stock value over time" report is upside down
- **Evidence:** CODE + LIVE.
- **What:** the value is computed as `rank × price`, where `rank` is `StockLevel.sequence`. But
  sequence **0 = Stocked, 1 = Low, 2 = Out** (`domain/stock_status.py`), and the loop does
  `if rank <= 0: continue`. Fully stocked items therefore contribute **$0**, and out-of-stock items count
  **2× their price**. Live, the well-stocked dense seed (31 stocked items) shows a flat **$7.00** every
  day.
- **Where:** `features/reports/reports.py:257-260, 322-339`. The only e2e test
  (`test_reports_router.py:45`) asserts `value >= 0`.
- **Also in the same report (STATIC):** with a linked product it adds the whole pack price; otherwise it
  falls back to a per-logged-unit cost (e.g. $0.008/g), so the units being summed are mixed. It also
  includes inactive products.
- **Likely origin:** the 2026-07-02 removal of the "Sufficient" level re-numbered the sequences; this
  report predates that.
- **Fix direction:** use the `stock_status` predicates to map level to a fill fraction (Stocked 1, Low
  ~0.5, Out 0) instead of the raw sequence, normalise to one price per item, and add a test with a known
  pantry.

### QA2-06 — Trim-to-budget never sees meal-plan demand
- **Evidence:** CODE (QA2 re-read).
- **What:** `_load_meal_demand` skips every ingredient with `ing.stock_item is None`. That relationship
  is `lazy="noload"` (`persistence/table_mappings.py:1598`) and isn't loaded by the query, so it is
  **always None**, and demand is always `{}`. As a result the "meal booked within 2 days — never cut"
  guard and tier 5 never fire, and tiers 1, 2 and 4 always treat "no short-term demand" as true.
- **Scenario:** rice is needed for tomorrow's dinner and is habit-bought and over $2. Expected: never
  cut. Actual: deferred as "Habit, can wait".
- **Where:** `features/shopping_lists/trim_to_budget.py:343,355`. `planned_demand.py:156` documents this
  exact trap and reads `_stock_item_id` instead. The unit tests inject `_MealDemand` directly, so the
  loader is untested.
- **Fix direction:** key by `_stock_item_id` as `planned_demand` does, and add a repo-level test that
  goes through the loader.

### QA2-07 — The meal-plan ingredient aggregate adds quantities in different units
- **Evidence:** CODE (QA2 re-read).
- **What:** the aggregate keeps the first non-None unit and adds raw quantities without calling
  `units.convert`.
- **Scenarios (STATIC):** 200 g flour + 1 kg flour → "201 g" (or "201 kg", depending on dict order);
  2 eggs + 1 dozen → "3 dozen"; 2 cups milk + 500 ml → "502 cup". The wrong total also feeds `meals_cost`
  and `to_buy_cost`.
- **Where:** `features/meal_plans/get_meal_plan_ingredients.py:131-143`. Tests only use one unit per item.
- **Fix direction:** convert into the item's canonical dimension before summing (mass → g, volume →
  ml, count → ea), and keep separate buckets for dimensions that can't be converted.

### QA2-08 — The expiry icon turns red ("Expired") from 10:00 on the expiry day, using a hardcoded 7-day window
- **Evidence:** STATIC. Two independent sub-audits found this.
- **What:** `new Date("2026-10-22")` parses as UTC midnight, which is 10:00 AEST, and is then compared
  against `Date.now()`. Before 10:00 the icon is amber; after 10:00 it is red, while the server and the
  alerts still say "expires today". The 7-day "soon" window is hardcoded, but the server's window is
  admin-configurable (`effective_expiring_soon_window`), so the icon and the "Expiring soon" filter
  disagree whenever the admin changes it.
- **Where:** `web_app/src/helpers/expiryIndicator.ts:21-27`, used by `StockItemRow.vue:499`,
  `StockItemDetailPage.vue:1998` and `ExpiringChip.vue:58,78`. No tests. FU-712 is open on the same file
  (tooltip formatting) but not this bug.
- **Fix direction:** have the server send the expiry state with each item (R-003: the server owns
  derived domain facts), or at minimum parse with `parseLocalIso`/`daysFromToday` and read the window
  from the server.

### QA2-09 — Server-voice (Piper) read-aloud and voice preview can't play: the CSP blocks `blob:` media
- **Evidence:** LIVE.
- **Repro:** on any page served by the app, `new Audio(URL.createObjectURL(<wav blob>)).play()` →

  Note that 'media-src' was not explicitly set"*.
- **Where:** `useSpeechOutput.ts:339-340` and `VoicePicker.vue:307-314` play server TTS through

- **Fix direction:** add `media-src 'self' data: blob:` and close FU-853 along with this.

## 4. Needs an owner decision

### QA2-41 — Should self-registration be open at all once an admin exists?
- See QA2-02. Options: closed (admin creates users), invite link, or open.
- **QA2 recommendation:** default closed with an admin toggle. Any internet-reachable install (Path
  B/A posture, Decision 5) can't ship with it open.

### QA2-42 — Should a finished ("done") shopping list accept new lines?
- **Evidence:** LIVE.
- **What:** `POST /shopping-lists/<done-list>/lines` → 200, and the line is added to a completed list.
  `start` on a done list is correctly refused (422).
- **Why it matters:** if it's intended ("I forgot to log something I bought"), it should be explicit
  in the UI. If not, it silently rewrites history that spend reports read.

### QA2-43 — Should email change require re-authentication?
- **Evidence:** STATIC.
- **What:** `PATCH /api/auth/me {"email": …}` changes the email with no password and marks it
  verified (`update_me.py:148`, recorded as a deliberate owner call). Combined with forgot-password, a
  briefly hijacked session becomes a permanent takeover. Worth revisiting alongside QA2-04.

### QA2-44 — What should an unknown recipe yield mean in costing and planning?
- **Evidence:** STATIC.
- **What:** `recipe.servings or 1` (`get_meal_plan_ingredients.py:106`, `build_week.py:249`) treats an
  unknown yield as 1 serving, so a blank-servings recipe planned at 4 has its demand and cost ×4. The
  saved plan (`get_meal_plans._hydrate_cost`) shows the same recipe as unpriced, so the week builder
  and the saved plan disagree. `apply_budget_cap` also counts unpriced recipes as $0, so a week of
  unpriced meals always passes the cap.

## 5. Further static-only leads (sub-audit, not re-verified by QA2)

Lower confidence or narrower impact. Confirm each before fixing.

- **Meal-plan aggregate ignores cooked portions on hand**
  (`get_meal_plan_ingredients.py:251-259`, same pattern in `auto_generate.py:363-372`).
  `allocate_pool` treats planned meals covered by frozen portions as needing nothing, so the shortfall
  report is empty while the rail says "needs 1 kg mince" and auto-generate adds it. Likely.
- **Savings measured against an offer the user never picked.** `_line_savings` falls back to
  `offers[0]` (`get_shopping_list_detail.py:252-270`). The fixture in `test_shopping_list_totals.py`
  copies the retired ladder.
- **Price observations are skipped whenever any offer exists** (`recipe_cost.py:420`), even when that
  offer can't price the unit.
- **Recipe cost price pick isn't deterministic** (`recipe_cost.py:168-216, 245-255`). The offer query
  has no ORDER BY, and it uses `is_available=False` products.
- **Waste "value at risk" price is arbitrary** (`waste/waste.py:107-122`). It takes the highest line
  `sequence`, not the cheapest last-paid price; the assistant's dollar framing reads it.
- **Missing-ingredient counts on meal-plan and recipe paths call `missing_count_for` without
  `levels_by_item`** (`get_meal_plans.py:624`, `get_recipes.py:563,566,599`), so they can disagree with
  the batch `cookable` if `stock_level` isn't loaded. Speculative.
- **Dora chat counts expired items as "expiring within a week"** and hardcodes 7 days
  (`services/doraIntents.ts:307,1110-1113,1145-1149`).
- **`import_spreadsheet.py:523` uses a naive `datetime.now()`**, which on a non-UTC host is stored as
  if it were UTC.
- **Export "generated at" times and filenames use the container zone** (`export_*.py`,
  `export_stock_overview.py:167`).
- **Assistant provider `base_url` + `/assistant/probe` reach internal hosts.** This is a documented,
  accepted trade-off; noted for completeness.

## Method notes (for whoever re-runs this)

- Ran from a detached worktree at a **short** path (`%TEMP%\qa2wt`), with `web_app/node_modules`
  junctioned from the main checkout. A worktree under the long scratchpad path fails on Windows path
  length, and the shared `web_app/dist` was being rebuilt by another session mid-run. Use your own
  worktree when another agent is active.
- Throwaway scripts (route crawl, API probe, flows, verification) lived in the session scratchpad,
  following the repo's "no feature Playwright specs" rule.
- **Cleanup:** the three servers were stopped, the throwaway DBs deleted, and the worktree removed with
  `git worktree remove`.
